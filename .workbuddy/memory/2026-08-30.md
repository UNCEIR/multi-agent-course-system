## Debug：recommend 接口空响应 + 前端 network error（已定位，未修复）

现象：POST /api/v1/recommend/stream 返回 200 但响应体为空，前端干等后 network error，后端无 ERROR 日志。

**"卡在 recall"是误判**——docker logs 证明 `agent.success agent=course_recall latency_ms=15.9`，recall 15~23ms 就完成。

根因链（有日志佐证）：
1. **主因**：`ai/llm_client.py:83-84` 建 httpx.Client/AsyncClient **未传 timeout**（httpx 0.28.1 默认 5s，但经 langchain-openai→openai SDK 后被 SDK 默认长超时覆盖）；`config/settings.py` 无任何 llm_timeout/request_timeout 配置项 → 单次 LLM 调用可挂数百秒，远超 profile 15s / supervisor 60s 的业务超时。
2. StudentProfileAgent 的 `await llm.ainvoke` 挂起 → phase1 `asyncio.gather(profile, recall)` 卡死 → **`course_supervisor.phase1_complete` 日志从未出现**（日志中确无此行）。
3. **可观测性黑洞**：profile 被取消时抛 `asyncio.CancelledError`（Py3.8+ 继承 BaseException），`agents/base_agent.py:43` 的 `except Exception` 抓不到 → 不打任何日志。这是"日志显示没问题"的直接原因。
4. phase1 gather 期间**不发任何 SSE 进度事件** → 前端干等 → 超时断开 → network error。
5. `supervisor.py:570` 捕获 CancelledError 打 `stream_cancelled`，流以 200 收尾（响应头已发）；uvicorn 访问日志因此显示 200 OK，极具迷惑性。

次生数据面问题：MySQL `fetch_courses row_count=0`、Milvus `status=empty` → 课程数据未导入 → recall 走 `_fallback_courses()` 返回 2 门硬编码假课（啤酒游戏/风景地貌学），并写入 Redis 反复 `cache_ids_stale`。

修复优先级：P0 给 httpx 加显式 timeout（并新增 settings 配置项）；P1 BaseAgent 补 `except asyncio.CancelledError`；P2 phase1 补发 SSE 进度事件；P3 跑 `ingest_course_dataset.py` 导入课程。

排查方法论要点：uvicorn 访问日志**在响应完成后才打印**，挂起的 SSE 请求不会留痕；排查须用 `docker logs <容器> 2>&1 | grep -v "GET /health HTTP"` 过滤掉前端 15s 轮询噪声，再按 request_id + 时间戳比对定位卡住的 phase。

**三个踩坑（重要）**：
1. `ChatOpenAI` 的超时字段叫 **`request_timeout`**，不是 `timeout`——传 `timeout=` 会被 pydantic **静默忽略**，超时保护形同虚设。
2. 只设 `httpx.Timeout` 不够：openai SDK 会用自身默认超时**覆盖**传入 httpx client 的配置（实测 27s 调用未触发 20s 超时）。两处都要设。
3. 测试用 `MagicMock()` 模拟 settings 时不包含新增字段，`httpx.Timeout(MagicMock())` 会抛异常 → 用 `getattr + isinstance` 兜底回退 None。

验证结果：profile LLM 27.4s → 5.7s；phase1 30s → 5s；全链路 53s 完整返回 done。测试 357 passed / 2 failed（2 个失败为容器环境差异，与改动无关：`_IncludedRouter has no attribute 'path'` 是 FastAPI 版本差异；`/python/memories/AGENTS.md` 是路径硬编码，容器内实为 `/app`）。
