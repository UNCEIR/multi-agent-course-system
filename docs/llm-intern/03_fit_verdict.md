## 方向一：AI Agent / LLM 应用开发

### Fit Verdict：🟢 强匹配

### 典型 JD 关键词覆盖

| JD 关键词 | 项目覆盖 | 证据强度 |
| --- | --- | --- |
| Multi-Agent / Agent 协作 | ✅ 5 个 Agent + Supervisor 编排 | 强（代码+测试） |
| Tool Use / Function Calling | ✅ 7 个 ReAct 工具定义 | 强（代码） |
| LLM 编排 / Orchestration | ✅ Pipeline + ReAct 双模式 | 强（代码） |
| Prompt Engineering | ✅ 各 Agent 独立 Prompt + 画像提取规则 | 中（代码，缺效果评估） |
| RAG / 检索增强 | ✅ Milvus 语义召回 + chunk 策略 | 中（代码，缺召回率评估） |
| Fallback / 降级策略 | ✅ Agent 基类 + 多层 fallback | 强（代码） |
| A/B 实验 | ✅ Thompson Sampling | 中（代码，缺实验结论） |
| 流式输出 / SSE | ✅ SSE + token 标记解析 | 中（代码，待补 E2E 测试） |

### 项目描述切换建议

**开场**（15 秒）：
> 我做的是一个 Multi-Agent 课程推荐系统，核心是探索 LLM 如何在有硬约束的场景里既发挥语义理解能力，又不引入概率错误。

**展开顺序**（3 分钟）：
1. 先讲 Multi-Agent 设计动机（规则保下限、LLM 提上限）
2. 再讲双模式编排（Pipeline 确定性 vs ReAct 灵活性）
3. 然后讲 Agent 的独立性和降级（每个 Agent 独立失败不阻断链路）
4. 补充 ReAct 安全网设计（硬约束锁死、循环后强制执行）
5. 最后讲 Tool Use 的工具设计（7 个工具、MANDATORY 标注）

**简历 bullet 推荐**：使用 `docs/resume-template.md`「版本一：AI Agent / 大模型应用」

### 面试高频追问预判

| 追问 | 准备 |
| --- | --- |
| "为什么自己写 Agent 循环，不用 LangGraph/CrewAI？" | 为精确控制硬约束锁死和 fallback，框架抽象层会增加调试复杂度 |
| "Agent 之间怎么通信？" | 当前是 Supervisor 集中调度，Agent 间通过 Phase 阶段的输入输出传递信息，无直接协商 |
| "ReAct 和 Pipeline 哪个更好？" | Pipeline 延迟可控适合正常请求，ReAct 适合异常场景。两者通过 A/B 实验共存是务实选择 |

### 项目描述切换建议

**开场**（15 秒）：
> 我做的是一个课程推荐系统的后端，FastAPI + MySQL + Milvus + Redis 四服务 Docker 部署，重点是缓存设计、API 容错和流式输出。

**展开顺序**（3 分钟）：
1. 先讲数据架构（MySQL 事实源 + Milvus 向量 + Redis 缓存，各自职责）
2. 再讲缓存设计（精确 key + 语义近邻 + 分布式锁防击穿，缓存只存 ID 回表验证）
3. 然后讲容错（Agent 基类重试+降级，每个环节失败不阻断链路）
4. 补充 embedding 优化（3 次降 1 次）
5. 最后讲流式输出（SSE + 状态机解析标记）

**简历 bullet 推荐**：使用 `docs/resume-template.md`「版本二：后端 / 工程能力」

### 面试高频追问预判

| 追问 | 准备 |
| --- | --- |
| "为什么 MySQL 端口是 3307？" | 避免与宿主机冲突，容器内仍用 3306 |
| "缓存击穿怎么处理？" | setnx 分布式短锁 + 缓存等待机制（0.1s×3） |
| "怎么保证缓存一致性？" | 缓存只存候选 ID，命中后回 MySQL 取最新数据，事实始终以 MySQL 为准 |
| "有压测吗？QPS 多少？" | 当前没有，是个人项目。有 Docker E2E 功能验证 |

## 方向三：推荐系统 / RAG

### Fit Verdict：🟡 中等匹配

### 典型 JD 关键词覆盖

| JD 关键词 | 项目覆盖 | 证据强度 |
| --- | --- | --- |
| 召回（Recall） | ✅ 多源召回（Redis→MySQL→Milvus→兜底） | 强（代码） |
| 粗排/精排（Ranking） | ✅ 规则预打分 + LLM 候选内重排 | 强（代码） |
| 向量检索 | ✅ Milvus COSINE + 1152 维 Embedding | 强（代码） |
| 硬约束/过滤 | ✅ 确定性规则过滤 | 强（代码） |
| 语义理解 / NLP | ✅ LLM 画像提取 + 语义初筛 | 中（缺效果评估） |
| 冷启动 | ❌ 未涉及 | 无 |
| 特征工程 | ✅ profile 特征 + chunk 文本特征 | 中（缺特征重要性分析） |
| 召回率/准确率评估 | ❌ 无离线评估 | 无 |
| 多样性 | ✅ 领域多样性保证 | 中（代码） |
| 可解释性 | ✅ 推荐理由生成 | 中（代码） |

### 项目描述切换建议

**开场**（15 秒）：
> 我做的是一个面向公选课场景的语义召回与可解释推荐系统，核心是让结构化过滤和语义理解分层协作——规则管确定性、LLM 管语义。

**展开顺序**（3 分钟）：
1. 先讲业务问题（500 门课 + 硬约束 + 语义偏好 → 分层推荐）
2. 再讲召回架构（MySQL 结构化 + Milvus 语义 + Redis 缓存，三源合并）
3. 然后讲 chunk 策略（四类分块避免语义稀释）
4. 然后讲评分职责分离（召回广度 vs 重排精度）
5. 补充硬约束过滤（确定性→LLM 语义初筛→重排，逐层收缩）
6. 最后讲可解释性（推荐理由生成）

**简历 bullet 推荐**：使用 `docs/resume-template.md`「版本三：推荐系统 / RAG」

### 面试高频追问预判

| 追问 | 准备 |
| --- | --- |
| "为什么不直接用协同过滤？" | 公选课场景缺少用户-课程交互矩阵，冷启动问题严重。当前基于内容+语义的方案更适合 |
| "召回率怎么评估？" | 当前没有离线标注集，是待补充项 |
| "chunk 策略为什么是 4 类不是更多？" | 4 类覆盖了课程的核心维度，更多会增加 Milvus 存储和检索延迟，需要在真实 query 命中分布上调整 |

## Fit Verdict 汇总

| 方向 | Verdict | 核心差异化 | 最大风险 |
| --- | --- | --- | --- |
| AI Agent / LLM 应用 | 🟢 **强匹配** | Multi-Agent 双模式编排 + 硬约束锁死 | 无真实用户指标 |
| 后端工程 | 🟡 **中等匹配** | 缓存设计 + 容错降级 + Docker | 无压测/CI |
| 推荐系统 / RAG | 🟡 **中等匹配** | 三层召回 + chunk 策略 + 评分分离 | 无召回率/CTR 评估 |
| 大模型算法 | 🔴 **弱匹配** | Agent 实践经验 | 无训练/微调经验 |
| 全栈 | 🔴 **弱匹配** | 不推荐 | 前端太薄 |

### 投递策略建议

1. **优先投**：AI Agent / LLM 应用方向 —— 项目匹配度最高，差异化最明显
2. **可投**：后端工程、推荐/RAG —— 需要切换描述侧重点，但核心能力可覆盖
3. **慎投**：大模型算法 —— 如果 JD 明确要求 SFT/RLHF 经验，不建议以此项目为主力
4. **不投**：全栈 —— 除非有其他前端项目补充
