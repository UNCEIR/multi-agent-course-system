# 04 — 证据升级计划

> 按时间紧迫度分级。每项升级都有明确的目标、步骤和产出。优先级：先补能直接用于面试回答的验证，再补能写入简历的量化指标，最后补长期工程优化。

---

## 半天（2-4 小时）

> 目标：补齐最基础的可验证证据，让每条关键声明都有当场可查的证据。

### U1. 运行全量单测并记录结果 ✅

- **步骤**：
  ```bash
  cd python
  python -m pytest tests/ -v --tb=short 2>&1 | tee test_results.txt
  ```
- **产出**：`test_results.txt` —— 面试被问"有测试吗？"时直接引用
- **写入**：更新 `docs/resume-template.md` 的测试通过数量
- **影响**：将"39 个单测通过"从二手信息升级为一手验证

### U2. Docker E2E 验证

- **步骤**：
  ```bash
  docker compose -f docker-compose.python.yml --profile python up -d
  docker compose -f docker-compose.python.yml --profile python ps
  # 等 30 秒服务就绪
  curl -sS -X POST http://localhost:8000/api/v1/recommend \
    -H "Content-Type: application/json" \
    --data-binary "@python/scripts/curl_recommend_payload.json" | python -m json.tool
  ```
- **产出**：API 返回的 JSON 响应截图/文本
- **写入**：在证据契约中补充"已验证通过"
- **影响**：当场证明系统可运行

### U3. SSE 流式端到端验证

- **步骤**：
  ```bash
  curl -sS -N -X POST http://localhost:8000/api/v1/recommend/stream \
    -H "Content-Type: application/json" \
    --data-binary "@python/scripts/curl_recommend_payload.json"
  ```
- **产出**：SSE 事件流输出文本
- **影响**：证明流式推荐真实可用

### U4. 代码行数统计

- **步骤**：
  ```bash
  find python/ -name "*.py" -not -path "*/.venv/*" | xargs wc -l
  find python/tests/ -name "*.py" | xargs wc -l
  ```
- **产出**：精确代码行数
- **影响**：简历中可写"约 XXXX 行 Python"而非模糊描述

## 一天（6-8 小时）

> 目标：补齐可写入简历的量化证据，让项目描述从"实现了什么"升级为"实现了什么+验证了什么"。

### U5. 代码覆盖率报告

- **步骤**：
  ```bash
  cd python
  python -m pytest tests/ --cov=. --cov-report=term-missing --cov-report=html
  ```
- **产出**：覆盖率百分比 + 未覆盖行列表
- **写入**：简历可加"测试覆盖率 XX%"
- **注意**：只在覆盖率确实 >70% 时写入简历，否则只内部参考

### U6. 硬约束过滤边界测试

- **目标**：验证已知的类别子串匹配局限
- **步骤**：
  1. 构造测试用例：
     - `"理工"` → 期望不匹配 `"自然科学与工程技术"`（已知局限）
     - `"计算机"` → 期望匹配含"计算机"的课程
     - `"文史"` → 期望匹配含"文史"的课程
  2. 运行 `HardConstraintFilter._fuzzy_text_match()` 单元测试
- **产出**：边界测试结果
- **影响**：面试被追问答类匹配准确率时，有具体测试数据而非模糊承认

### U7. 召回质量抽样评估

- **目标**：手工评估至少 5 个典型 query 的召回质量
- **步骤**：
  1. 设计 5 个典型 query（如：纯兴趣型、纯约束型、混合型、冷门领域、模糊需求）
  2. 记录每个 query 的召回数量、Top-10 课程
  3. 人工判断前 10 是否相关
- **产出**：召回质量抽样表格
- **影响**：面试被问"召回质量怎么样？"时，有抽样数据可展示
- **注意**：不做虚假精确度声明，只做定性描述

### U8. ReAct 实验组激活 + 对比

- **目标**：实际运行一次 ReAct 模式，对比 Pipeline 输出差异
- **步骤**：
  1. 在 `ab_test.py` 中临时将 `react_vs_pipeline` 实验所有用户路由到 `react` 组
  2. 用同一个 payload 分别调用 Pipeline 和 ReAct
  3. 对比：推荐课程列表差异、延迟差异、token 消耗差异
- **产出**：Pipeline vs ReAct 对比记录（课程重叠率、延迟倍数）
- **影响**：面试问"ReAct 比 Pipeline 好吗？"时，有真实对比数据

## 三天（15-20 小时）

> 目标：补充项目差异化亮点，让面试时有"只有我做了"的故事可讲。

### U9. 离线评估框架（召回率 + MRR）

- **目标**：构建最小可用离线评估
- **步骤**：
  1. 手工标注 20 个 query 的相关课程（每个 query 标注 3-5 门相关课）
  2. 计算 Recall@10、MRR
  3. 对比不同配置（有无语义缓存、不同 chunk 策略、有无 Milvus）的指标
- **产出**：离线评估脚本 + 评估结果表格
- **影响**：简历可写"手工标注 20 query 离线评估集，Recall@10 = XX%"

### U10. LangGraph 对比实现

- **目标**：用 LangGraph 重写核心编排，形成架构对比
- **步骤**：
  1. 用 LangGraph StateGraph 实现同等 Pipeline
  2. 对比代码量、可读性、调试难度
  3. 记录迁移中的设计取舍
- **产出**：LangGraph 实现 + 对比文档
- **影响**：面试时展示"我不是只会自己写，也会评估框架"，差异化很强

### U11. Prompt 版本 A/B 对比

- **目标**：对至少一个 Agent（推荐画像或重排）做 Prompt 版本对比
- **步骤**：
  1. 设计 2 个 Prompt 变体
  2. 用 10 个 query 跑两组，人工判断输出质量
  3. 记录结论
- **产出**：Prompt A/B 结果记录
- **影响**：展示 Prompt Engineering 的迭代思维

### U12. 快速体验 Demo（非 Docker）

- **目标**：提供不需要 Docker 的快速体验方式
- **步骤**：
  1. 写一个 `demo.py` 脚本，mock 掉 MySQL/Milvus/Redis 依赖
  2. 用硬编码的 20 门课和 mock 向量跑完整链路
  3. 输出推荐结果
- **产出**：`python/demo.py` —— 面试官可当场运行
- **影响**：现场展示能力——面试时"让我看看实际效果"可以直接跑

## 一周（30-40 小时）

> 目标：补齐项目成为"强项目"的关键缺口。

### U13. 真实课程数据质量审计

- **目标**：审计 500 门课的数据质量，发现并记录问题
- **步骤**：
  1. 检查字段完整率（缺失值比例）
  2. 检查时间/校区/容量字段的一致性
  3. 检查 chunk 文本质量（乱码、截断、空值）
  4. 输出数据质量报告
- **产出**：数据质量报告
- **影响**：在推荐系统方向面试中展示"数据质量意识"

### U14. 时间冲突检测增强

- **目标**：从当前的轻量检查升级为完整的时间冲突矩阵
- **步骤**：
  1. 解析课程时间字段（星期几 + 第几节）
  2. 计算课程间时间重叠
  3. 在推荐结果中标注冲突课程对
- **产出**：时间冲突检测模块 + 测试
- **影响**：硬约束从"单课约束"升级到"课程间约束"

### U15. 用户行为闭环（最小可用）

- **目标**：实现最简的反馈收集→指标计算链路
- **步骤**：
  1. 添加 `POST /api/v1/feedback`（click/like/skip）
  2. 存储到 MySQL 或 JSON 文件
  3. 简单统计（每门课的点击率、Top-N 命中率）
- **产出**：反馈 API + 统计端点
- **影响**：简历可写"实现了用户反馈闭环"，从静态推荐升级为有反馈的系统

### U16. CI/CD（GitHub Actions）

- **目标**：添加最简 CI 流水线
- **步骤**：
  1. 添加 `.github/workflows/test.yml`
  2. 跑 pytest（mock 掉外部依赖）
  3. 跑代码风格检查（ruff/flake8）
- **产出**：CI 流水线
- **影响**：后端工程方向的重要加分项
