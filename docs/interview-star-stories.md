# 面试 STAR 故事库

<!-- markdownlint-disable MD024 -->

本文档用于把项目讲成“做过的人会怎么复盘”。每个故事都按“原来问题、我改了什么、如何验证、哪里还能追问”组织。真实未知的业务指标统一标为“待补充”。

## 故事一：把历史电商推荐收敛为公选课推荐主线

### 一句话

把“商品推荐”改造成“学生选课决策”，并让文档、代码和接口讲同一条主线。

### S 情境

项目早期保留了不少电商推荐表达，例如商品、营销文案、库存决策、CTR 等。后来主线已经转成学校公选课推荐，但如果继续沿用旧话术，面试时会出现代码在讲课程、文档在讲电商、简历在讲泛推荐的问题。

### T 任务

我的任务是把对外叙事收敛到当前可运行的 Python 公选课链路：学生输入自然语言偏好，系统返回课程列表、推荐理由、风险提醒和 Agent 执行轨迹。

### A 行动

- 我把推荐对象从商品改成课程，围绕 `StudentProfile`、`Course`、`CourseRecallResult` 等课程模型讲主线。
- 我把 Agent 职责重新解释为学生画像、课程召回、课程重排、硬约束/可行性、推荐理由。
- 我把历史电商计划标注为 Legacy，只保留迁移背景，不再混入当前项目主叙事。
- 我在面试材料中删掉无法证明的 CTR、P99、百万级数据，用“完整闭环”“接口可验证”“测试通过”替代虚构指标。

### R 结果

现在项目可以用一条清晰主线讲完：从课程 CSV 到 MySQL/Milvus/Redis，再到 FastAPI 推荐接口和 SSE 流式输出。真实业务指标仍待补充，不在简历中编造。

### 60 秒口播

这个项目一开始有不少电商推荐的遗留表达，但当前可运行主线已经是学校公选课推荐。如果面试时还讲商品、库存和营销文案，就会和代码不一致。所以我把项目叙事重新收敛到“学生选课”这个场景：学生用自然语言描述需求，系统从真实课程数据里召回候选，排序、过滤风险，再生成理由。这个整理也让我明确哪些能力可以写，比如 Redis 召回候选缓存、Milvus chunk 召回、硬约束过滤；哪些不能写，比如未验证的 CTR、P99 和实时学生画像。

### 可追问点

- 为什么保留历史字段而不是全部删除？
- 哪些内容是 Legacy，哪些是当前主线？
- 如何避免简历和代码不一致？

## 故事二：课程数据从 CSV 到 MySQL + Milvus 的召回闭环

### 一句话

把课程事实和语义检索拆开，既能按字段过滤，也能理解自然语言偏好。

### S 情境

公选课推荐既有结构化条件，也有语义偏好。校区、时间、容量、年级限制适合用数据库字段判断；“给分友好”“作业少”“不要考试”更像自然语言语义。如果只用 MySQL，会难以理解模糊需求；如果只用向量库，又难以保证课程事实完整和约束准确。

### T 任务

我要设计一个课程数据层，让召回能同时支持结构化过滤和语义匹配，并且最终推荐结果可回溯到真实课程记录。

### A 行动

- 我把课程 CSV 写入 MySQL `course_records`，保留完整课程事实。
- 我把每门课拆成 `basic`、`schedule_capacity`、`learning_profile`、`audience_tags` 四类 chunk，写入 `course_chunks` 和 Milvus。
- 我让 Milvus 只负责返回相关 chunk/course ID，最终仍通过 MySQL 回表拿完整课程。
- 我把 `course_milvus_collection` 对齐为 `course_chunks_real`，维度按项目配置使用 1152。

### R 结果

容器内曾完成前 50 门课程导入验证：MySQL 中 `course_records=50`、`course_chunks=200`，Milvus 有效实体与 MySQL chunk 集合一致。全量 500 门导入需要在当前环境重新执行后再写成结果。

### 60 秒口播

课程数据层我做了一个取舍：不是把整行 CSV 直接丢进向量库，而是同时保留 MySQL 主表和 Milvus chunk。MySQL 负责课程事实，比如校区、时间、容量和限制条件；Milvus 负责自然语言语义，比如“作业少”“给分友好”。每门课拆成四类 chunk 后，用户问学习体验就更容易命中 `learning_profile`，问时间和容量就更容易命中 `schedule_capacity`。最后推荐结果一定回 MySQL，所以不会只展示向量片段。

### 可追问点

- 为什么不整行 embedding？
- chunk 设计怎么影响召回质量？
- MySQL 回表如何保持 Milvus 排序？
- 导入失败后如何校验 MySQL 和 Milvus 一致？

## 故事三：Redis 召回缓存与语义近邻命中

### 一句话

缓存候选 ID，不缓存课程事实，减少重复召回但不牺牲准确性。

### S 情境

多个学生可能反复问类似需求，例如“找轻松不考试的艺术课”。如果每次都重新走 MySQL 宽召回和 Milvus embedding 检索，成本和外部依赖波动都会增加。但课程容量、已选人数又会变化，不能简单缓存完整课程对象。

### T 任务

我要让相似需求复用召回结果，同时保证最终课程字段仍然来自最新 MySQL 数据。

### A 行动

- 我用结构化画像字段生成 Redis cache key，缓存候选 `course_id` 列表。
- 命中缓存后仍调用 MySQL `fetch_courses_by_ids()` 回表。
- 对同一个 key 增加 Redis 短锁，降低同类并发请求同时击穿召回链路的风险。
- 后续补充语义缓存索引，让语义相近 prompt 也能命中，响应中能看到 `cache_match_type=semantic`、`milvus_skipped=true` 等观测字段。

### R 结果

相关测试覆盖了缓存命中跳过 Milvus、缓存未命中写入候选 ID、Redis 不可用时回退完整召回。Docker 端到端验证中，语义相近样例出现 `redis_recall_cache_semantic_hit`，命中时跳过 Milvus。

### 60 秒口播

Redis 这里我没有缓存完整课程对象，因为热门课程的容量和已选人数会变。我的缓存对象是“某类画像对应的候选 course_id 列表”。命中后还要回 MySQL，这样课程事实仍然新。为了避免多个相似请求同时未命中，我给同一个 key 加了短锁，第一个请求构建缓存，其他请求短暂等待再读。后来又补了语义近邻命中，让措辞不同但意思接近的 prompt 也能复用召回结果。

### 可追问点

- 为什么不缓存完整 `Course`？
- 语义缓存命中会不会误伤硬约束？
- Redis 不可用时系统怎么降级？
- 缓存 TTL 和短锁 TTL 为什么要分开？

## 故事四：硬约束过滤从软打分中独立出来

### 一句话

用户明确要求的条件不能只靠排序分数表达，必须有确定性过滤门槛。

### S 情境

原先可行性检查偏轻量，硬冲突主要看时间，校区、课程类别、老师、不考试等条件容易被当成软偏好。这样用户明确说“只要西校区”时，系统仍可能推荐其他校区课程。

### T 任务

我要把“必须满足”的硬约束从 LLM 排序和软偏好里独立出来，避免违规课程进入最终推荐。

### A 行动

- 我在画像模型中增加硬约束字段，区分天然硬约束和强意图才升级的约束。
- 我在 Supervisor 中插入 Phase 1.5 `HardConstraintFilter`，先过滤再进入重排。
- 我让 CourseFeasibilityAgent 更专注于容量、爆满等风险提醒，不再承担所有硬过滤职责。
- 我在流式接口中增加 `phase15_complete` 事件，让前端能感知硬约束过滤阶段。

### R 结果

相关单测和 Docker 验证显示：指定“西校区 + 自然科学类”时，最终课程均满足约束；结果少于请求数量时会返回 `requested_count_shortage` warning，而不是偷偷放宽条件。

### 60 秒口播

我后来发现一个问题：如果把所有偏好都交给排序分数，用户明确说“只要西校区”时，系统仍可能因为别的分数推荐其他校区。这类需求不应该只是软分数，所以我在 Phase 1 和 Phase 2 之间加了硬约束过滤。画像 Agent 提取出校区、类别、不考试等硬约束，过滤器先把不符合的课程挡掉，再让 LLM 在剩余候选里排序。如果过滤后课程不够，我返回 warning，而不是自动放宽条件。

### 可追问点

- 哪些算硬约束，哪些算软偏好？
- 如果硬约束过滤后没有课程怎么办？
- 为什么不让 LLM 自己判断硬约束？
- Phase 1.5 为什么放在召回后、重排前？

## 故事五：同步推荐与 SSE 流式推荐对齐

### 一句话

让长链路推荐过程可见，避免用户等到最后才看到结果。

### S 情境

推荐链路包含画像、召回、过滤、重排、理由生成等阶段。同步接口能返回最终结果，但前端或演示时无法看到中间进度；同时历史脚本里曾使用 `/api/v1/stream_recommend`，代码实际注册的是 `/api/v1/recommend/stream`，容易造成 404。

### T 任务

我要让流式接口和主链路一致，并把阶段事件和理由 token 流稳定输出。

### A 行动

- 我让 `/api/v1/recommend/stream` 和 `/api/v1/stream_recommend` 走同一套响应封装。
- 我修正 Phase 3 调用参数，让 `astream_reasons()` 使用 `profile=`。
- 我把流式超时语义调整为只约束 Phase 3 token 流，避免前置阶段耗时挤占全部预算。
- 我在 SSE 序列中保留 `phase1_complete`、`phase15_complete`、`phase2_complete`、`phase3_complete`、`done` 等事件。

### R 结果

`python/tests/test_stream_recommend.py` 通过 5 个测试；Docker 验证中 `/health`、同步推荐和流式推荐均返回成功，SSE 序列包含阶段事件和 token 输出。

### 60 秒口播

流式接口这块我主要解决两个问题：一个是路由别名不一致，另一个是 Phase 3 token 流的超时语义不准确。我把两个流式路径统一到同一套实现，并让超时从理由生成开始算，而不是从整个推荐入口算。这样前面画像和召回慢一点时，不会一进入理由阶段就被误判超时。最终 SSE 能把阶段进度和推荐理由 token 都推给前端。

### 可追问点

- SSE 和普通同步接口共用了哪些逻辑？
- 为什么 Phase 3 超时不从请求入口算？
- 流式失败时前端能收到什么事件？
- Phase 1.5 事件对用户有什么价值？
