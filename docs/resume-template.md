# 项目/经历 STAR 包装

本文档用于把“学校公选课 Multi-Agent 推荐系统”包装成简历、面试口播和追问回答。原则是少堆技术名词，多讲业务问题、个人动作、决策原因和真实边界。

## 一句话电梯稿（20 字内）

把学生选课偏好转成可解释推荐

## S 情境

- 背景与约束：学校公选课数量多，学生选课时不只看课程名，还会同时考虑兴趣、校区、时间、考试、作业量、给分友好度、容量和专业/年级限制。传统关键词搜索很难理解“不要考试、作业少、周三晚上不要、有点热门也可以冲”这类混合诉求。
- 为何会演变成当前架构：因为选课推荐不是单次生成答案，而是“理解学生 -> 找真实课程 -> 排序 -> 检查风险 -> 解释原因”的连续决策，所以拆成多个职责清晰的 Agent。

## T 任务

- 目标：把一个历史推荐项目改造成面向教务系统的公选课 Multi-Agent 推荐系统，让学生输入自然语言 prompt 后，系统返回课程列表、推荐理由、选课风险和 Agent 执行轨迹。
- 你的职责范围：我负责 Python 主链路的场景建模、Supervisor 编排、课程数据导入、MySQL/Milvus 召回设计、5 个 Agent 的职责拆分，以及面试可讲清楚的文档整理。

## A 行动（重点：改动与决策，不是技术清单）

- 原来怎么做 / 问题在哪：原项目和文档偏电商推荐叙事，容易讲成“用户画像、商品召回、营销文案”的通用推荐系统；但当前业务已经转为学校公选课，如果继续沿用电商说法，面试时会出现 README、架构文档和代码主线不一致的问题。
- 我具体做了什么：我把推荐对象从商品抽象成课程，新增/使用 `StudentProfile`、`Course`、`CourseRecallResult` 等课程模型；用 `SupervisorOrchestrator` 编排学生画像、课程召回、课程重排、选课可行性、推荐理由 5 个 Agent；把课程 CSV 拆成 `basic`、`schedule_capacity`、`learning_profile`、`audience_tags` 四类 chunk，分别写入 MySQL 和 Milvus；针对多个学生反复问相似需求的情况，我新增 Redis 召回缓存，只缓存结构化画像对应的候选 `course_id` 列表，并用短锁降低同类并发请求同时击穿 MySQL/Milvus 的风险。
- 为什么这样选 / 没选什么替代方案：没有让 LLM 直接生成课程，因为那样容易推荐数据集中不存在的课，也无法可靠处理时间冲突、容量、年级和专业限制；也没有缓存完整 `Course` 对象，因为热门课的容量和已选人数变化快，缓存完整对象容易不准。我选择“Redis 缓存候选 ID + MySQL 回表 + LLM 重排 + 规则可行性检查”，让缓存只减少重复召回成本，课程事实仍以 MySQL 为准。

## R 结果

- 可验证结果：项目形成了从 `public_elective_courses.csv` 导入 MySQL/Milvus，到 Redis 召回缓存，再到 `POST /api/v1/recommend` 返回课程、理由、风险和 Agent 轨迹的完整闭环；新增测试覆盖了缓存命中跳过向量检索、缓存未命中写入候选 ID、Redis 不可用回退完整召回，以及 Supervisor 主链路使用缓存候选仍能返回推荐结果。
- 仍不完善之处 / 若再问怎么优化：当前 Redis 已用于召回候选 `course_id` 缓存，但还没有真正接入学生实时画像；时间冲突仍是字符串匹配，A/B 和 metrics 是进程内轻量实现。后续会优先做标准课表时间段模型、实验结果持久化和真实学生行为特征。

## 口播版（60～90 秒）

我做的是一个学校公选课 Multi-Agent 推荐系统，解决的是学生选公选课时需求很复杂的问题。比如学生会说“不考试、作业少、给分友好，最好东校区，周三晚上不要有课”，这不是简单课程名搜索能处理的。

我的做法是把选课推荐拆成 5 个 Agent：学生画像 Agent 先把自然语言转成结构化偏好；课程召回 Agent 先查 Redis 是否已有相似画像的候选课程 ID，没有命中再用 MySQL 和 Milvus 从真实课程数据里找候选课；课程重排 Agent 在候选课程 ID 内做个性化排序；选课可行性 Agent 检查容量、时间冲突、年级专业限制；最后推荐理由 Agent 生成面向学生的解释。

数据层上，我没有把整行 CSV 直接向量化，而是把每门课拆成基础信息、时间容量、学习体验、适合人群四类 chunk。这样学生说“不要考试、作业少”时，更容易命中学习体验相关片段；同时 MySQL 保留完整课程记录，负责结构化过滤和回表展示。

这个项目最后能跑通从课程 CSV 导入 MySQL/Milvus，到 Redis 召回缓存，再到 FastAPI 推荐接口返回课程、理由、风险提醒和 Agent 执行轨迹的闭环。当前不足是时间冲突判断还比较轻量，后续会改成标准课表时间段模型。

## 展开版（2～3 分钟）

这个项目的背景是公选课推荐比普通关键词搜索复杂。学生通常不会只搜“艺术课”，而是把很多约束混在一句话里，比如“对电影心理学感兴趣、不想考试、作业少、东校区优先、周三晚上不要”。这些需求有的偏语义，有的是强约束，有的是风险偏好。如果让一个 LLM 直接生成课程，很容易出现两个问题：一是推荐数据集中不存在的课，二是对容量、时间、专业限制这类结构化条件处理不可靠。

所以我把链路拆成了 Supervisor + 5 个 Agent。Supervisor 里第一阶段并行跑学生画像和课程宽召回。画像 Agent 负责把 prompt 结构化成兴趣、领域、校区、避开时间、考试和作业偏好；召回 Agent 先用原始 prompt 从 MySQL 和 Milvus 里找候选。画像出来后，如果有领域或校区这类强约束，再补一次结构化召回。第二阶段并行做课程重排和可行性检查，重排 Agent 只允许 LLM 从候选课程 ID 里排序，可行性 Agent 用规则检查时间冲突、容量、年级、专业和先修。最后再生成推荐理由。

数据导入这块我做了一个比较关键的取舍：没有把 CSV 每一整行直接 embedding，而是拆成四类 chunk。`basic` 存课程名、教师、领域；`schedule_capacity` 存校区、时间、容量、热度；`learning_profile` 存考核、难度、作业量、是否考试、是否小组作业；`audience_tags` 存年级专业限制、先修和适合人群。Milvus 负责按自然语言命中 chunk，MySQL 负责保存完整记录和规则过滤。比如用户说“不要考试、作业少、给分友好”，更容易打到 `learning_profile`，然后再通过 `course_id` 回表拿完整课程。

这个项目的结果是形成了完整闭环：`ingest_course_dataset.py` 可以把真实公选课 CSV 导入 MySQL 和 Milvus，`/api/v1/recommend` 可以返回课程列表、推荐理由、风险提醒和每个 Agent 的执行结果。针对多个学生同时询问类似需求的场景，我加了 Redis 召回缓存，它缓存的是候选 `course_id` 列表，命中后仍回 MySQL 拿最新课程状态；如果多个请求同时未命中同一个画像 key，会用 Redis `SET NX EX` 短锁让一个请求优先构建缓存，其他请求短暂等待后复用。比较诚实地说，现在还有工程化不足，比如 A/B 和 metrics 还是进程内的，Redis 还没真正接入实时学生画像，时间冲突也只是字符串匹配。

## 高频追问回答

### 为什么不用一个大 prompt 直接推荐？

因为选课推荐有强数据约束。课程必须来自真实 CSV/MySQL，时间、容量、年级、专业和先修要求也不能靠 LLM 猜。我的设计是让 LLM 做画像抽取、候选内排序和理由生成，数据真实性和硬约束交给数据库和规则 Agent。

### 为什么课程要拆 chunk？

整行课程信息字段太杂，直接 embedding 会让“时间容量”“学习体验”“适合人群”混在一起。拆 chunk 后，用户问“不要考试、作业少”会更容易命中 `learning_profile`，问“东校区、别太难抢”会更容易命中 `schedule_capacity`。

### MySQL 和 Milvus 怎么分工？

Milvus 负责语义相关性，比如“轻松”“给分友好”“艺术兴趣”。MySQL 负责完整课程记录、结构化过滤和回表展示，比如校区、时间、容量、教师、学分、年级专业限制。最终推荐结果必须回到 MySQL 的课程 ID 和字段。

### Redis 缓存为什么只存 course_id？

因为这个缓存解决的是“相似需求反复召回”的成本，不是替代课程事实源。热门课的容量、已选人数和限制条件变化比较快，如果缓存完整课程对象就可能过期；只缓存候选 `course_id`，命中后再回 MySQL 拿最新字段，能兼顾性能和准确性。

### 多个同学同时问相似需求怎么办？

我按结构化画像生成 cache key，只对同一个 key 使用 Redis 短锁。第一个未命中的请求拿到锁后执行完整召回并写缓存，其他请求短暂等待后再读缓存；如果等待后仍未命中，就回退完整召回，保证主链路不被缓存层拖死。

### Supervisor 并行是怎么设计的？

我先分析 Agent 依赖。画像和宽召回都可以基于原始请求开始，所以 Phase 1 并行。重排和可行性检查都依赖候选课程，但互不依赖，所以 Phase 2 并行。推荐理由必须等最终课程和风险提醒出来，所以串行。

### 如何降低 LLM 幻觉？

重排阶段只允许输出候选课程 ID，推荐理由只能基于传入字段生成，最终课程都来自 MySQL 回表。解析失败时会回退规则排序或字段拼接理由，不会让 LLM 自由编造课程。

### 爆满课程为什么不直接过滤？

因为真实选课里爆满课不一定没价值。它可能非常符合学生兴趣，只是抢课风险高。所以我把爆满作为软风险提醒，而不是硬过滤；时间冲突、专业限制、缺少先修才属于硬冲突。

### 这个项目现在最大的不足是什么？

我会坦诚说三个：时间冲突判断还是字符串匹配，应该升级为标准课表时间段模型；A/B 和 metrics 是进程内实现，缺少持久化；Redis 目前用于召回缓存，Feature Store 还没有真正接入学生实时行为画像。

## 简历注意事项

### 推荐写法

- 用“公选课推荐”“教务选课场景”“自然语言偏好”开头，不要一上来就堆 Multi-Agent。
- 简历 bullet 尽量包含动作对象，比如“拆分 CSV 为四类 chunk”“约束 LLM 只输出候选课程 ID”。
- 不要写无法证明的指标，例如 CTR 提升、P99 延迟、百万级数据，除非你确实有压测或实验记录。
- 可以写“完整闭环”“可解释推荐”“风险提醒”“Redis 召回候选缓存”，这些能从当前接口、代码和测试验证。

### 不推荐写法

- “使用 LangGraph、Milvus、Redis、Docker 搭建系统”太像技术栈罗列。
- “实现高并发推荐系统”当前没有压测支撑，不建议写。
- “Redis 实时画像”当前主链路未真正使用 Redis 特征，不建议写成已实现能力；可以写“Redis 召回候选缓存”。
- “A/B 测试平台”当前是进程内实验框架，建议写“保留实验分组框架”。
