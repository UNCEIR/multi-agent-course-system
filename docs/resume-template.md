# 简历 Bullet 与口播模板

本文档只放可直接用于简历和面试口播的表达模板。完整 STAR 故事见 `docs/interview-star-stories.md`，追问训练见 `docs/interview-question-bank.md`。

## 1. 写简历前的边界

可以写：

- 公选课推荐、教务选课场景、自然语言偏好。
- Supervisor 编排、5 个 Agent、候选内排序、硬约束过滤、推荐理由。
- MySQL 课程主表、Milvus chunk 语义召回、Redis 候选 `course_id` 缓存。
- Docker、FastAPI、同步推荐接口、SSE 流式推荐接口。
- 已验证的测试结果，例如具体测试文件通过、Docker E2E 记录、接口返回 200。

不要写：

- 真实用户 CTR、CVR、GMV、P99 延迟等没有验证的数据。
- “百万级高并发”“生产级推荐平台”等当前没有压测或上线证据的表述。
- “Redis 实时学生画像”，当前主线是召回候选缓存。
- “全量 500 门课程已在当前环境稳定导入”，除非你当次环境已重新验证。

## 3. 简历 Bullet 模板

### 版本一：AI Agent / 大模型应用

```text
• 设计并实现面向教务选课场景的 Multi-Agent 推荐系统，支持学生用自然语言描述兴趣、校区、时间、考核方式和学习负担偏好
• 采用 Supervisor 模式编排学生画像、课程召回、课程重排、硬约束过滤/可行性检查、推荐理由生成等阶段，将选课决策拆成可追踪、可降级的链路
• 将 LLM 限定在画像抽取、候选课程内排序和推荐理由生成，最终课程均来自 MySQL 回表结果，降低推荐不存在课程的风险
• 为流式推荐链路补充 SSE 事件序列，支持从 Phase 1 到 Phase 3 的阶段进度与 token 输出展示
```

### 版本二：后端 / 工程能力

```text
• 基于 FastAPI 提供 /api/v1/recommend、/api/v1/recommend/stream、/health、/metrics 等接口，并通过 Supervisor 统一承接推荐业务逻辑
• 使用 asyncio.gather 按依赖关系并行调度 Agent：画像与宽召回并行，硬约束过滤后重排与可行性检查并行，推荐理由串行依赖最终课程
• 封装 Agent 基类，统一处理耗时记录、指数退避重试和 fallback，避免各 Agent 重复实现运行时保障逻辑
• 为课程召回增加 Redis 候选 ID 缓存与同 key 短锁，缓存命中时跳过 Milvus 检索，命中后仍回 MySQL 获取最新课程状态
```

### 版本三：推荐系统 / RAG

```text
• 构建“结构化过滤 + 语义召回 + 候选内重排”的课程推荐链路，支持学生用自然语言表达复杂选课偏好
• 将课程 CSV 拆分为 basic、schedule_capacity、learning_profile、audience_tags 四类 chunk，提升“作业少、不考试、给分友好”等需求的语义命中稳定性
• 使用 MySQL 保存完整课程事实并承担校区、分类、容量等精确字段过滤，使用 Milvus 承担自然语言语义召回
• 使用 Redis 缓存“结构化画像/语义近邻 -> 候选 course_id 列表”，减少相似选课需求重复执行宽召回和向量检索的成本
```

## 4. 60 秒口播模板

```text
我做的是一个学校公选课 Multi-Agent 推荐系统。它解决的问题是：学生选公选课时不只看课程名，还会同时考虑兴趣、校区、时间、考试、作业量、给分和容量，比如“不考试、作业少、东校区，周三晚上不要有课”。

我的做法不是让 LLM 直接生成课程，而是把链路拆成几个阶段。学生画像 Agent 把 prompt 转成结构化偏好和硬约束；课程召回 Agent 结合 Redis、MySQL、Milvus 从真实课程数据里找候选；硬约束过滤会先挡掉明确不符合要求的课程；重排 Agent 只在候选课程 ID 内排序；最后推荐理由 Agent 生成解释。

数据层上，我把课程 CSV 同时落到 MySQL 和 Milvus。MySQL 保存完整课程事实，Milvus 保存四类 chunk 的 embedding，Redis 只缓存候选 course_id，命中后仍回 MySQL 拿最新容量和限制。这个设计的结果是推荐更可追踪，也更容易解释哪里失败、哪里降级。

当前不足也比较明确：时间冲突仍偏轻量，A/B 和 metrics 是进程内实现，真实业务指标还需要上线后补充。
```

## 5. 3 分钟展开模板

```text
这个项目最开始容易讲成普通推荐系统，但公选课场景其实有更强的约束。学生说“轻松、给分友好”是语义需求，说“东校区、周三晚上不要”是硬约束，说“热门但可以冲”是风险偏好。如果用一个大 prompt 直接让 LLM 推荐，很容易推荐不存在的课程，也很难证明时间、容量、专业限制处理得可靠。

所以我把系统拆成 Supervisor + 多个 Agent。Phase 1 里，学生画像和宽召回并行，因为召回可以先基于原始 prompt 开始。画像出来后，如果有校区、课程类别、不考试等强约束，再做补充召回。Phase 1.5 是确定性硬约束过滤，避免用户明确说西校区却混入东校区课程。Phase 2 里，重排和可行性检查并行，最后 Phase 3 才生成推荐理由。

课程数据我没有整行直接 embedding，而是拆成 basic、schedule_capacity、learning_profile、audience_tags 四类 chunk。这样用户说“不考试、作业少”时更容易命中学习体验相关文本；用户说“东校区、别太难抢”时更容易命中时间容量相关文本。Milvus 命中后只返回 chunk/course ID，最终展示和规则判断都回 MySQL 拿完整课程字段。

后来我又补了 Redis 召回缓存。它缓存的是候选 course_id 列表，不是完整课程对象，因为课程容量和已选人数可能变化。命中缓存后仍回 MySQL，这样既减少重复 Milvus 检索，也保证课程事实最新。验证上，项目有缓存命中、硬约束过滤、流式推荐和 Docker 接口调用记录；真实业务指标还没有，所以简历上不会写 CTR 或延迟提升。
```

## 6. Bullet 自检

- [ ] 每条 bullet 有具体动作对象，例如“拆分 CSV 为四类 chunk”，不是只写“使用 RAG”。
- [ ] 结果只写能证明的现象或测试，不写虚构指标。
- [ ] 能区分“我负责的改动”和“项目已有能力”。
- [ ] 对 Legacy 电商内容只写迁移背景，不写成当前主线。
- [ ] 技术栈后面能讲出为什么用它，而不是只罗列。
