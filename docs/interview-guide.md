# 学校公选课 Multi-Agent 推荐系统：面试准备主入口

本文档是面试准备的入口，不再承载所有细节。它负责回答三个问题：这个项目怎么讲、先练哪几段、被追问时去哪里找证据。

## 1. 一分钟项目介绍

我做的是一个学校公选课 Multi-Agent 推荐系统。学生不用按课程名搜索，而是直接说自己的选课偏好，例如“不考试、作业少、给分友好、东校区，周三晚上不要有课”。系统会先把自然语言拆成学生画像和硬约束，再从真实课程数据里召回候选课，之后在候选课程内排序、检查容量和时间等风险，最后生成推荐理由。

这个项目的重点不是“用了很多 Agent”，而是把选课推荐拆成了几类能被验证的决策：理解学生、找真实课程、排序、过滤硬约束、解释推荐原因。这样讲起来更像做过工程，而不是背技术名词。

## 3. 面试主叙事

### 3.1 开场顺序

1. 先讲场景：学生公选课选择不是单一关键词搜索，而是兴趣、时间、校区、考核、容量和限制条件混在一起。
2. 再讲原问题：历史文档和部分模型来自电商推荐，直接照搬会让当前项目叙事和代码主线不一致。
3. 再讲改动：我把主线收敛到 Python/FastAPI 的公选课推荐链路，拆出 5 个 Agent，并把课程数据落到 MySQL、Milvus、Redis。
4. 最后讲验证：导入、推荐接口、流式接口、硬约束、Redis 缓存都有对应测试或端到端记录；未知或未生产化的指标用“待补充”。

### 3.2 一句话架构

> 我没有让 LLM 直接生成课程，而是先从学生 prompt 抽画像和硬约束，再用 MySQL、Milvus、Redis 从真实课程数据里召回候选，之后只在候选课程内排序，并用规则检查时间、容量和限制条件，最后生成可解释建议。

### 3.3 三个必须讲清的取舍

- **为什么不是一个大 prompt**：课程必须来自真实数据，时间和容量不能靠 LLM 猜，所以让 LLM 做画像、排序和解释，让数据库和规则承担事实与硬约束。
- **为什么拆 5 个 Agent**：每个阶段的输入输出、失败回退和观测指标不同。拆开后可以并行，也能定位问题发生在画像、召回、排序、硬约束还是理由生成。
- **为什么 Redis 只缓存 `course_id`**：缓存目标是减少重复召回成本，不是替代课程事实源。命中缓存后仍回 MySQL 拿最新容量、限制和课程字段。

## 4. 训练路径

### 第一轮：讲顺

- 用 `docs/interview-star-stories.md` 的“主故事”练 60 秒口播。
- 要求：不超过 90 秒，不连续堆 3 个技术名词，每 20 秒都能听到“为什么”或“我做了什么”。

### 第二轮：讲细

- 用 `docs/code-walkthrough.md` 练代码证据链。
- 要求：能从 `python/main.py` 讲到 `SupervisorOrchestrator`，再讲到 `CourseRecallAgent`、`HardConstraintFilter`、`RecommendationReasonAgent`。

### 第三轮：被追问

- 用 `docs/interview-question-bank.md` 练追问。
- 要求：每题先给一句结论，再给一个代码或验证证据，最后承认一个真实边界。

## 5. 不要这样讲

- 不要说“实现了高并发推荐系统”，当前没有压测数据支撑。
- 不要说“CTR 提升 15%”，项目没有真实用户实验结果。
- 不要把 Redis 说成“实时学生画像”，当前主链路用的是召回候选缓存。
- 不要说“全量生产可用”，当前 A/B、metrics 仍是进程内实现，时间冲突也不是完整课表算法。

## 6. 面试前自查

- [ ] 30 秒内能讲清“学生选课为什么难”。
- [ ] 能说清“历史电商项目如何迁移到公选课主线”。
- [ ] 能解释 MySQL、Milvus、Redis 分别解决什么问题。
- [ ] 能说明 Phase 1、Phase 1.5、Phase 2、Phase 3 的依赖关系。
- [ ] 能拿出至少一个验证证据：导入、单测、Docker E2E、SSE、Redis 缓存或硬约束过滤。
- [ ] 对真实未知数据使用“待补充”，不编造指标。
