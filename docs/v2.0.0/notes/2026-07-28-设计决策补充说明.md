## 决策 8 补充：跨语言 TS 集成（MCP 桥接）具体做法与原理

**补充（2026-07-28）：具体做法 + 决策原理（结合多轮对话 + subagent 源码调研）**

本决策经 4 轮对话沉淀：①原始澄清（TS 项目二次开发集成）→ ②「为什么不用 HTTP/RPC」质疑 → ③「为什么不考虑 RPC」追问 → ④委派 subagent 实地读 FastGPT `mcp_server` 源码 + 查 MCP 规范。以下为 grounded 结论。

### 一、具体做法（subagent 实地源码确认）

FastGPT `mcp_server`（`E:\Agent\FastGPT\projects\mcp_server\src\index.ts`）实测：
- **传输层 = SSE（旧规范）**：`SSEServerTransport`，`GET /:key/sse` 建连 + `POST /:key/messages?sessionId=...` 发请求，Express 监听 PORT（默认 3000）。`key` 是 FastGPT 后台创建的 MCP key，绑定若干 app。
- **暴露的是 FastGPT app**（simple/workflow/workflowTool 三类），`callMcpServerTool` = 运行该 app 的 workflow（`dispatchWorkFlow`）。
- **两层跨进程**：Python ↔ mcp_server（MCP/SSE）→ mcp_server ↔ FastGPT 主服务（HTTP `/api/support/mcp/server/toolList|toolCall`）。mcp_server 是薄适配层。
- **Python 端接入**：`langchain-mcp-adapters` 的 `MultiServerMCPClient`，`transport="sse"`，url=`http://<host>:<port>/<key>/sse`；`load_mcp_tools` 一行把 FastGPT app 转成 LangChain `StructuredTool`，deepagents 直接用。
- **v2.0.0 范围**：先接 FastGPT 这 1 个 TS 服务（pi/cc 后续）。

### 二、关键发现：MCP + HTTP 共存（修正原记录笼统说法）

FastGPT mcp_server **只暴露 app，不暴露底层 KB 管理操作**（upload/split/embed/dataset CRUD）。故：
- **MCP 主链路**：agent Q&A（`query_knowledge` tool 调 FastGPT KB-Q&A app，动态发现）
- **裸 HTTP 补充**：KB 管理操作（upload/split/embed）走 FastGPT HTTP admin API，Python 侧包成少量 LangChain tool
- 两者共存。原决策 8 笼统说「MCP 桥接」漏了 HTTP 这层。

### 三、决策原理

1. **MCP 本质是 JSON-RPC 2.0**——即一种 RPC。「用 MCP」=「用一种特化的 RPC」（面向 LLM agent 工具发现）。故「为什么不考虑 RPC」的准确回答：**考虑了，用的就是 RPC（JSON-RPC），只是没选 gRPC 那种 protobuf 强类型 RPC**。
2. **不选 gRPC 的硬证据**：① FastGPT 是 NextAPI/Express 架构，无 gRPC 接口，加一层要侵入式改造 + protobuf 双端 codegen；② 性能瓶颈在 LLM + workflow 执行（秒级），传输层 SSE vs gRPC 的毫秒级差异被完全淹没，性能无关；③ gRPC 强 protobuf 契约把 Python/TS 在 schema 层强耦合，与二次开发项目要松耦合、API 会演进的需求反向；④ LangChain 有原生 MCP client（自动注册 tool），无原生 gRPC-to-tool，gRPC 还要手写 wrapper。
3. **MCP 优于裸 HTTP（主链路）**：① FastGPT 已实现 mcp_server，零改造成本；② `tools/list` + JSON Schema 让 agent 动态发现工具——FastGPT 后台加 app → Python agent 自动多一个工具，零代码改动；③ MCP 是 LLM agent 工具生态既定标准（LangChain/Claude/OpenAI Agents 原生支持），裸 HTTP 不是。
4. **裸 HTTP 在 KB 管理路径反而更优**：固定后端操作（upload/split/embed），不需 agent 发现，HTTP 更简单、可 curl 调试，且 FastGPT mcp_server 本就不暴露这些。
5. **边界条件**：若只需调一个固定 FastGPT app、不需动态发现，裸 HTTP 调 FastGPT 的 OpenAI 兼容端点（`/api/v1/chat/completions`）最简单；但一旦 agent 要在多 app 间自主选择或 app 增删，MCP 动态发现更省事。

### 四、跨进程通信原理背景

底层只有三类：字节流 / 消息队列 / 共享内存。HTTP/gRPC/JSON-RPC/MCP 都架在 TCP 或本地字节流之上。MCP 传输三种：stdio（本地父子进程）、SSE（旧，FastGPT 用的）、Streamable HTTP（新，2025-03-26 起，`Mcp-Session-Id` 会话管理）。握手：`initialize` → server 返回 capabilities → `notifications/initialized` → client 主动 `tools/list` / `tools/call`（client 主动 pull 工具列表，非 server push）。

### 五、待决/风险
- FastGPT mcp_server 用旧 SSE 规范（已 deprecated，新规范是 Streamable HTTP）——v2.0.0 可用，后续可跟进。
- 外网抓取受企业代理限制，MCP 官方规范细节依据 WebSearch + 源码交叉验证；Phase 0 POC 核对官方最新文档。
- FastGPT KB 存储拓扑（自带 Mongo vs 复用 MySQL/Milvus/MinIO）仍待决（与决策 6 开放项一致）。

## 决策 5 修订补充（2026-07-28）：批量 Excel → 1.html → WeasyPrint PDF

基于 `E:\Agent\1.html` 实际报告 + 用户流程，决策 5 从"单学生 MVP + CSV"修订：

- **范围**：批量（所有学生），非单学生
- **输入**：每科 Excel（一个 Excel = 该科全体学生成绩），非 CSV
- **报告形态**：`1.html` 模板填表（学业质量评价学生成绩报告单，固定表格：道德与法治/语文/数学/英语/科学/社团/音乐/体育/美术/信息/劳动/综实；每科含 过程性评价 + 展示性评价(30%) + 考试性评价(70%) + 综合性评价(100% 期末总评)）
- **复合统计**：加权 `期末总评 = 展示性评价×30% + 考试性评价×70%`（确定性，**Python 算，option D**，不跨 FastGPT，不用 LLM 算——防幻觉）
- **流程**：每科 Excel →（LLM 或 openpyxl 提炼）单科学生 JSON → 整合以学生为单位 JSON → 遍历每学生：Python 算加权 + 填 `1.html` 模板(Jinja2) → **WeasyPrint 渲染 PDF** → **每学生独有 PDF 下载链接**（非总 zip）
- **报告输出**：PDF（WeasyPrint）——1.html 本就是 HTML，WeasyPrint 直接渲染 colspan/rowspan 表格最优；**修订决策 7**（docxtpl Word → WeasyPrint PDF）
- **报告闭环不跨 FastGPT**：统计(pandas)+模板填表(Jinja2)+PDF(WeasyPrint) 全 Python；LLM 只做 Excel 提炼
- **成绩统计方案**：option D（Python 算加权 + Python 填数值字段 + LLM 只产文本段）——企业级评审全维度最优，契合需求.md"理性+感性"分工
- **学段一致性**：`1.html` 仅作结构参考（表格布局模板），实际报告用大学公选课；决策 14（MySQL `course_records` 富化）适用
- **待决**：Excel→JSON 解析方式（openpyxl vs LLM，看样本）

### 为什么复合统计用 Python 而非 FastGPT Code 节点 / LLM

FastGPT 源码调研：FastGPT 无专用成绩统计节点/模板，复合统计靠 Code 节点（JS/Python 沙箱）+ LLM 节点分工。我们 Python 原生（option D）不照搬沙箱——deepagents 本身是 Python，已有更强执行环境，沙箱徒增可测/可维护/性能劣势。LLM 直接算统计被排除（算术不可靠、幻觉风险，违背防幻觉）。

## 智能体重构补充（2026-07-28）：统计 agent + 评价寄语 agent

> **重构**：原"评语体系 agent"（score JSON→进步/突出/排名 comment）并入**成绩统计智能体**作"成绩记载功能"；另立**评价寄语 agent**（comment_type 驱动）。两个独立智能体，页面不同，**对话不共享**。

### 成绩统计智能体（`/report`）
在报告卡（1.html→WeasyPrint PDF）基础上增加：
- **成绩记载功能**（原评语体系并入）：score JSON → 进步/突出/排名/最优成绩 comment，作"报告的评价数据转换"
- **流式评价叙述**：AI 对话中流式述说每个学生的评价（参考 image-1）
- **回答穿插**：在回答中穿插成绩记载的回答
- **下载流程**：每学生独有 PDF 下载链接（非总 zip）
- **参考**：image-2（大学生期末课程背景）、image-3（批量下载 word，原参考）、image-1（流式成绩记载叙述）

### 评价寄语 agent（`/evaluation`）
- **输入**：studentList JSON（学生数组），单个学生：`{studentId, studentName, comment_type, teacherSubjectiveEvaluation, scoreList[]}`
  - **comment_type 四种**：赞扬鼓励型 / 客观评价型 / 温情关怀型 / 幽默风趣型

- **输出**：`{studentId, studentName, comment}` —— comment **结合 comment_type** 输出
- **输出示例**（赞扬鼓励型）：`{"studentId":"S2025001","studentName":"林宇","comment":"林宇同学，你在学习中展现出的热情与努力老师都看在眼里！..."}`
- **实现**：LLM 按 comment_type + teacherSubjectiveEvaluation + scoreList 生成评语（score 数值是输入，禁 LLM 自算——防幻觉）
- **参考**：image.png（教师寄语→大学生成绩评语）
- **架构**：独立端点 `/evaluation`；Phase 2；与统计 agent 对话不共享，前端两个不同 agent 页面

## 决策 3 补充：框架 = deepagents（2026-07-28）

**建在 LangGraph 之上**：`create_react_agent` + StateGraph——保留 v1 LangGraph 投资 + 中转站 ChatOpenAI 兼容（复用 `langchain-openai` + `one.zhique.cn`）。

**额外获得**：内置虚拟文件系统（中间产物落盘=防幻觉）+ TodoWrite 规划 + subagent 委派。

**subagent 拓扑**：
- 主 deep agent（`/chat`）：TodoWrite 规划 + 路由 + tool/subagent 委派
- **subagent**（需推理/规划）：报告 subagent（`/report`，批量 Excel→PDF 多步）、评价寄语 agent（`/evaluation`，comment 生成）
- **tool**（确定性，无推理）：`recommend_courses`（v1 推荐包装）、`query_knowledge`（KB Q&A 检索）、`compute_weighted_grade`（复合统计）、`transcript_parser`（Excel 解析）等
- 专用端点 `/report` `/evaluation` 直达对应 subagent（绕过主 agent，决策 10）

**文件系统使用场景（防幻觉核心）**：
- 报告生成：单科 JSON、学生 JSON、加权 stats 落盘 → LLM 读回填模板，引用文件而非记忆（不 hallucinate 数值）
- 评价寄语：score JSON 落盘 → LLM 读文件生成 comment（数值引用正确）
- 文档摄入：上传文档存文件系统 → 分切/向量化
- 长对话：compaction 摘要落盘 → 恢复时引用
- 通则：多步任务的中间状态落盘，每步 grounding 在文件，不塞 context window

**vs OpenAI Agents SDK**：SDK 有 handoffs/guardrails/MCP + TS 变体，但无文件系统；deepagents 更适合文档生成场景。

**风险**：实验性包，Phase 0 POC 验证与中转站+Docker 兼容（go/no-go 门）；"deepagents-on-LangGraph" WebSearch+源码交叉验证，未本地源码核实。

**配置**：`deepagents>=0.1.0`（已加 requirements），经 ChatOpenAI 接中转站；无 TS 变体（与决策 8 MCP 桥接不冲突）。

## 决策 7 补充：Skills 系统 = 原生 tools + 单模型双渲染（2026-07-28）

**注册模式**：原生 Python 工具（`@tool`/工厂函数，Pydantic 生成 JSON Schema，非手写），in-process 调用。

**ToolRegistry 接口**：
- `register(tool)`：注册内置 tool
- `register_mcp(server_url)`：注册 MCP-backed tool（经 `langchain-mcp-adapters` 加载 FastGPT mcp_server 工具）
- `get_all(allowed=None)`：返回 tool 列表，按 allowlist 过滤（权限门控）
- 启动时注册内置 tool，运行时可动态注册 MCP tool

**Pydantic schema 示例**（`compute_weighted_grade`）：
- Input：`display_eval: float`、`exam_eval: float`、`weights: dict = {display:0.3, exam:0.7}`
- Output：`final_grade: float`、`level: str`（分档）
- `@tool(args_schema=WeightedGradeInput)` → LangChain 自动生成 JSON Schema 给 LLM

**MCP-ready 抽象**：`ToolRegistry` 统一管理原生 tool + MCP tool，agent 经 `get_all()` 拿到合并池（决策 8 实操）。

**报告渲染**：Jinja2 HTML（1.html 模板）→ WeasyPrint PDF（决策 5 修订，docxtpl Word 作废）。

**Skills 清单**（v2.0.0）：`recommend_courses`、`query_knowledge`、`compute_weighted_grade`、`transcript_parser`、`report_renderer`（Jinja2+WeasyPrint）、`evaluation_generator`（评语 LLM）、`web_search`（tavily）、`mcp_client`（FastGPT）。

**源码印证**：pi/claude-code/OpenMAIC/FastGPT 4 项目全部原生工具为主，MCP 仅外部能力可选层。

**权限**：allowlist gate（参考 OpenMAIC），敏感操作门控。

**位置**：`python/skills/`（ToolRegistry 注册层）+ `python/tools/`（具体 tool 实现）。

## 决策 9 补充：报告获取推荐 = 共享 tool（2026-07-28）

**推荐能力 = `recommend_courses` tool**（决策 4 定义 schema：input `query`/`student_id`/`constraints`，output `courses`/`warnings`/`experiment_group`）。

**报告 subagent 调用数据流**（"选课建议"步骤）：
1. 报告 subagent 接收学生 JSON（成绩 + 画像）
2. TodoWrite 规划：①Excel→JSON ②整合学生 JSON ③MySQL 富化 ④算加权统计 ⑤填模板 ⑥选课建议（调 `recommend_courses`）⑦渲染 PDF
3. 步骤⑥：
   - 构造 input：`query` = 从画像/成绩提炼的选课偏好（如"偏好不考试、作业少的理工课"）、`student_id`、`constraints`（已修课程排除）
   - 调用 `recommend_courses` → 返回排序课程列表（含 score/reason）
   - 课程列表**落盘**（文件系统，防幻觉）
   - LLM 读文件生成"下学期选课建议"文本段落（引用 tool 返回课程，不自算）
4. 段落填入报告模板对应区域

**主 agent（`/chat`）同接口调用**：用户问"推荐课程"时，主 agent 调同一 tool。

**理由**：推荐是确定性 pipeline，tool 无多余 LLM hop（vs nested subagent 多一层推理）。

**细化决策 4**：v1 暴露为 tool，uniformly callable。

**防幻觉**：选课建议文本由 LLM 生成，但课程列表/分数来自 tool 确定性结果，LLM 不自算。

## 决策 11+12 补充：可靠性 = deepagents 内置 + v1 + 源码模式（2026-07-28）

### 决策 11 上下文管理/防幻觉
- deepagents 文件系统 + TodoWrite（中间产物落盘，不塞 context window）
- compaction（阈值 `context tokens > effectiveContextWindow - 13000`；保留最近 `keepRecentTokens=20000` tail；前面历史用 LLM 生成结构化摘要）
- **compaction 摘要模板**：
  - Goal：用户目标/任务
  - Progress：已完成步骤
  - Key Decisions：关键决策
  - Next Steps：下一步
  - Critical Context：必须保留（学生ID、已修课程、报告状态等）
  - 摘要落盘，恢复时引用
- subagent 上下文隔离（forkedAgent 模式，报告/评价寄语互不污染）
- 工具懒加载（ToolSearch，非必要工具不进 prompt）
- 文件读取截断（大文件 offset 分段）

### 决策 12 失败兜底
- v1 `BaseAgent` 重试/兜底（tenacity，已验证）保留
- deepagents checkpointing（LangGraph 持久化，可恢复）
  - **存储后端**：复用 v1 Redis 作 LangGraph checkpointer（自定义 `RedisSaver`，避免新增存储；备选 `SqliteSaver` 本地持久）
  - `thread_id`（会话ID）→ 加载 checkpoint → 从中断点恢复
  - 存 graph state（节点输出、工具调用、消息历史）
- 工具 try/catch → isError result（pi/claude-code 模式）
- circuit breaker（连续 3 次失败熔断，避免死循环）
- 部分结果保留（extractPartialResult，长任务中断不丢进度）
- 权限门控（allowlist gate）

**源码印证**：claude-code（autoCompact/circuit breaker/AgentTool）、pi（compaction/emitRunFailure）、OpenMAIC（allowlist gate）。

## 决策 14 补充：数据模型 + MySQL 富化（2026-07-28）
