# 2026-08-04 项目文件架构重构

## 背景与问题

- **本轮要解决的问题**：`python/` 目录包放置杂乱，`services/` 混装 LLM 工厂、A/B 引擎、指标、SSE 解析器、电商遗留等 9 个不同职责的文件；`agents/` 和 `orchestrator/` 平铺无层次；电商时期遗留代码（feature_store/intent_templates/milvus_repository/15+ 电商枚举）未清理。v2.0.0 要引入多个企业级智能体（report/evaluation/chat/documents + deepagents harness + tools + skills），若不先重构基座，目录会变成"诗山"。
- **触发原因**：用户明确要求参考 `E:\Agent\pi` 的目录结构，完完全全重构当前项目结构，要求有层次感，为后续 v2.0.0 多智能体扩展腾出空间。
- **影响范围**：`python/` 下全部 30+ 个 .py 文件，涉及 50+ 处 import 改动，6 处 sys.path hack，Dockerfile/docker-compose/CLAUDE.md/README.md 同步更新。

## 总体架构方案

- **设计思路**：参考 pi 的 monorepo 分层模式（`packages/ai` → `packages/agent` → `packages/coding-agent` → `packages/server`），映射为 Python 的 `ai/` → `agent/` → `app/` → `storage/` 等分层。
- **分层依赖方向**：`app/`（应用层）→ `agent/`（v2 运行时预留）→ `ai/`+`storage/`+`experiment/`+`observability/`（基础设施）→ `config/`+`models/`（全局契约）。`config/` 和 `models/` 留顶层，因为被所有层引用。
- **关键设计取舍**：
  - `ai/` 包同时放 `tracing.py`（功能属 observability 但启动时序紧耦合 ai/）
  - `stream_token_markup_parser.py` 放 `app/recommend/`（公选课专用，不进 ai/ 基础设施层）
  - `base_agent.py` 留在 `app/recommend/agents/`（v1 专用，v2 用 deepagents 不共享）
  - `main.py` 模块化拆分为 `app/main.py`（薄层装配）+ `app/runtime.py`（单例容器）+ `app/api/`（路由模块）
  - docker-compose 删除所有 `profiles: ["python"]`，实现 `docker compose up -d` 一键启动

### 核心逻辑

- **git mv 保留历史**：所有文件移动用 `git mv`，git 历史可追溯，旧文件不在仓库中。
- **sys.path 统一指向 python/**：`app/main.py` 的 `sys.path.insert` 改为 `os.path.dirname(os.path.dirname(__file__))`（指向 python/）；scripts/tests 的 path hack 不变。
- **import 风格统一**：子模块直 import（`from app.recommend.agents.student_profile_agent import StudentProfileAgent`），`__init__.py` 保留懒加载 re-export 作兼容。
- **运行时单例容器化**：`app/runtime.py` 管理所有全局单例（supervisor/repos/ab_engine/metrics），`init()`/`shutdown()` 生命周期方法，api 路由从 runtime 取依赖避免循环 import。

### 兼容性与风险控制

- 4 阶段分步提交，每阶段跑 `compileall` + `pytest` 验证，出错可回滚。
- 旧包 `__init__.py` 仍保留懒加载 re-export 作兼容，但已删除旧目录（services/agents/orchestrator/repositories 的 __init__.py 已清理）。
- 保留 4 个 agent_timeout 字段（`user_profile`/`product_recall`/`product_rerank`/`marketing_copy`/`inventory`），因为 agent 代码里使用了这些字段名，未来重构 agent 时再重命名。

## Debug 结论

- **根因**：无 Debug 问题，所有 import 错误在编译阶段发现并修复。
- **排查过程**：
  1. 阶段 1 compileall 发现 `storage/mysql/course_repo.py` 的 `from .mysql_repository import` 路径不对 → 改为 `from .base import`
  2. 阶段 2 pytest 发现 `test_tracing.py` 的 `patch("services.tracing.get_settings")` 路径不对 → 改为 `patch("ai.tracing.get_settings")`
  3. 阶段 3 清理 settings 时过度删除了 agent_timeout 字段，导致 5 个测试失败 → 恢复 4 个实际使用的字段
  4. 阶段 3 清理 schemas 时误删了 `PriorityAdvice` 类 → 恢复并调整定义顺序（`PriorityAdvice` 在 `CourseFeasibilityResult` 之前定义）
- **解决方式**：按错误提示逐步定位修复，每个修复后跑 `compileall` + `pytest` 确认。

## 经验与后续

- **本轮经验**：
  1. **grill-me 预决策极大减少返工**：重构前用 grill-me 逐一确认 20+ 个子决策（顶层包结构、目录命名、import 风格、迁移顺序等），避免中途改方向。
  2. **subagent 调研是决策质量的保证**：派 Explore agent 精读 `services/` 9 个文件的 import 引用链，确认 feature_store/intent_templates 零引用才敢删；参考 pi 目录结构确保设计有依据。
  3. **sys.path hack 是最大的陷阱**：`main.py` 迁到 `app/main.py` 后，`os.path.dirname(__file__)` 指向 `app/` 而非 `python/`，必须改为 `os.path.dirname(os.path.dirname(__file__))`，否则所有顶层包 import 崩。
  4. **settings.py 的 agent_timeout 字段不能全删**：agent 代码里硬编码引用了 `settings.agent_timeout_product_recall` 等字段名，虽然这些是电商遗留命名，但删除字段会改 agent 行为，重构期间只清理不重命名。
  5. **Docker registry 网络问题是持续约束**：Docker Hub 需要代理或镜像，`docker compose up -d` 验证需在可用网络环境执行。
- **后续建议**：
  - 有网络时执行 `docker compose up -d --build` + `curl /health` + `curl /api/v1/recommend` 完成端到端验证
  - 阶段 2 用的 `sed -i` 批量改 import 在已有 `__pycache__` 时可能漏文件，建议下次先用 `find . -name "__pycache__" -exec rm -rf {} +` 清理
  - 重构后 `app/runtime.py` 的 `mysql_repo`/`redis_repo`/`course_vector_repo` 单例在 `app/api/health.py` 中被引用为 `runtime.mysql_repo`，但 `health.py` 的 `_health_payload()` 中使用了 `if runtime.mysql_repo:` 判断，这是安全的。
