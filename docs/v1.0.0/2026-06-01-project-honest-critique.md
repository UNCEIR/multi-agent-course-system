# 项目诚实评价：亮点与短板

## 背景与问题

- 本轮要解决的问题：在面试文档全量优化完成后，客观审视项目的真实竞争力和短板，避免面试时"讲过头被拆穿"
- 触发原因：用户要求对项目做一次诚实评价
- 影响范围：面试叙事策略、口播节奏、追问准备

## 总体评价

在校招实习项目这个定位下，质量相当不错。但有明显短板需要在面试中诚实应对。

核心判断：**诚实 + 有细节 > 包装 + 被拆穿**。

---

## 真正的亮点

### 1. 工程成熟度远超典型校招项目

大部分同学的"推荐系统项目"停留在"调了个 API + 写了个 prompt"。本项目有完整的数据闭环（CSV → MySQL → Milvus → Redis → API → 前端），有真实的降级链路（每个 Agent 都有 fallback），有缓存设计（精确 + 语义 + 短锁），有流式输出（SSE + marker parser 状态机）。

### 2. 迭代深度

26 篇 notes 记录了 5/11-5/28 的真实迭代过程。语义缓存误命中、embedding 冗余消除、评分职责分离——这些不是一开始设计好的，而是用了之后发现问题再改的。面试官最想听的就是"原来 → 问题 → 改动 → 验证"的链条。

### 3. "规则保下限、LLM 提上限"叙事

不是空话。硬约束过滤确实是纯规则、LLM 确实只在画像/排序/理由三个环节参与、每个环节确实有 fallback。能把这个讲清楚，比说"我用了 Multi-Agent"强十倍。

## 真实的短板（面试必须准备的防御）

### 短板 1："多 Agent"的含金量

**问题**：Agent 之间没有对话、没有协商、没有质疑。本质上是 Supervisor 按固定顺序调用函数，每个函数碰巧叫"Agent"。ReAct 模式是往真正的 Agent 方向迈了一步，但 A/B 都没注册，等于没有真实运行过。

**面试官可能的追问**：
- "你的 Agent 之间有什么交互？"
- "这跟一个普通的 FastAPI + LangChain 后端有什么区别？"

**防御策略**：
- 承认当前是"编排器调度 + LLM 增强"，而非自主协作 Agent
- 用"关注点分离 + 独立 fallback + 可观测"来解释拆分价值
- 指出 ReAct 已实现但在对比阶段，诚实说明现状
- 不要说"Agent 协作系统"，说"多阶段 Agent 编排"

### 短板 2：没有任何真实用户数据

**问题**：没有 CTR、没有用户满意度、没有 A/B 实验结果、没有线上延迟数据。

**面试官可能的追问**：
- "你怎么知道推荐是好的？"
- "有没有量化的效果指标？"

**防御策略**：
- 诚实回答：当前是工程验证而非效果验证
- 能证明的：单测覆盖链路正确性（39 passed）、Docker E2E 接口可达、硬约束过滤有确定性验证
- 不能证明的：推荐质量本身没有度量
- 主动说出来："真实业务指标需要上线后补充，我不会编造"

### 短板 3：部分设计"做了但没验证效果"

**问题**：
- `_compute_score()` 的 0.5 系数——经验值，没有调参
- 语义缓存阈值 0.95——经验值
- 四类 chunk 的拆分方式——没有对比实验证明比整行 embedding 好
- LLM 语义初筛——没有对比实验证明比规则预筛好

**面试官可能的追问**：
- "你做了很多优化，怎么证明有效？"
- "0.5 这个系数怎么选的？"

**防御策略**：
- 承认是经验值，解释选择的推理过程
- 说明理想方案（大量真实 query 做 A/B 调参），但当前没有条件
- 强调"工程决策在信息不完整时也需要做，关键是有兜底"

### 短板 4：技术栈偏"组装"而非"深入"

**问题**：MySQL、Milvus、Redis、LangChain、FastAPI——每个都用了，但每个都没有深入到让人印象深刻的程度。

**具体表现**：
- Milvus 只用了最基本的 search，没有 partition、没有自定义索引策略
- Redis 缓存设计不错但没有集群模式考量
- MySQL 没有读写分离或分库分表
- LangChain 主要用 ChatOpenAI 和 bind_tools，没有深入 LCEL 或自定义 Chain

**面试官可能的追问**：
- "你在 Milvus 上做了哪些调优？"
- "Redis 如果挂了怎么办？"
- "500 门课，为什么需要 Milvus？MySQL FULLTEXT 不够吗？"

**防御策略**：
- 承认当前规模不需要分布式优化，但解释选型理由
- Milvus 的价值不是规模，是"语义召回 vs 结构化过滤"的分工
- Redis 跳过缓存走完整召回已有降级路径，单点但不影响正确性
- 避免硬说"高可用设计"，说"单机验证阶段，架构支持横向扩展"

## 按岗位的竞争力评估

| 方向 | 竞争力 | 原因 |
|---|---|---|
| AI Agent / 大模型应用 | **较强** | ReAct + Pipeline 双模式、硬约束锁死、LLM 参与度分层——校招中属于有深度的理解 |
| 后端工程 | **中等偏上** | 完整数据层 + 缓存 + 流式，但缺少高并发、分布式、消息队列等后端硬指标 |
| 推荐系统 | **中等** | 有召回-排序-过滤 pipeline，但没有离线训练、没有特征工程、没有 AB 实验结果 |

## 面试生死线

**能不能在被追问时保持诚实但不崩盘。**

最大的风险不是"做得不够好"，而是"讲过头了"：
- 说"Multi-Agent 协作系统"但被追问发现 Agent 之间没有交互 → 扣信任分
- 说"规则保下限、LLM 提上限，当前是编排器调度模式" → 面试官觉得有清醒认识

**口播节奏要求**：每 20 秒都有一个"为什么"或"我发现了什么问题"。

---

## 经验与后续

### 本轮经验
- 项目亮点在于迭代深度和工程成熟度，而非技术栈的广度或深度
- 短板的防御策略核心是"诚实 + 有推理过程"，不是回避
- "做了但没验证效果"是最难回答的追问方向，需要额外准备

### 后续建议
- 如果有时间，做一个简单的对比实验：四类 chunk vs 整行 embedding 的召回命中率对比
- 考虑注册 ReAct A/B group 并跑一次真实请求，让"已实现但未注册"变成"已实现已验证"
- 准备 2-3 个"我曾经犯过的错误"的小故事（语义缓存误命中、embedding 冗余、Phase 3 超时语义），这些是最能体现"做过感"的素材
- 针对每个短板准备一个 30 秒的"承认 + 解释 + 如果有更多时间我会怎么做"的回答模板
